Autopilot for your job search

Your job search, running itself.

One agent finds the roles that fit you, tailors a résumé from facts you have verified, applies wherever the employer published a route, and moves each application along as the replies come in. You decide how hands-off it is.

01 · how it works

From posting to reply, without the busywork.

Every four hours one pass runs all four steps. Each card below is drawn from that pass's real output, captured from the engines in this repository.

01 · find

It watches the boards so you don't.

Searches every connected provider with terms taken from your own résumé, classifies each posting, and ranks by deadline before score.

02 · prep

A résumé per role, fact-checked.

Assembled only from evidence you verified, reworded in the posting's own vocabulary, and blocked if any claim cannot be traced back.

03 · apply

Submitted, or waiting for your yes.

Goes out through the employer's own API or published address. Until you switch it to hands-off, each one waits for a tap.

04 · track

Replies move the pipeline.

Recruiter mail is classified and linked to its application, so the status updates itself. High-stakes replies stay drafts until you send them.

02 · the chain

Nothing is evaluated out of order.

A job is not a match until the steps before it have cleared. Country decides which rulebook applies; the rulebook decides whether you can legally hold the role at all; only then does skill overlap mean anything. Each stage below is a real module, and each one can stop the chain.

    04 · where the jobs come from

    Every board, by a route it actually permits.

    Twenty-five providers, declared as data. Google Jobs returns LinkedIn, Indeed, ZipRecruiter, Glassdoor, Monster, CareerBuilder and Dice listings in one query, each naming its origin — which is kept as the job's board, so per-board conversion analytics still mean something. Google Search reaches the Workday, Taleo and iCIMS pages no aggregator carries, reading each posting from the schema.org block the employer publishes for exactly that purpose.

    Then the open developer APIs — Adzuna and Jooble cover both the United States and India — the partner APIs, the RSS feeds, and the per-employer board APIs for a company you are specifically targeting. Four work with no key at all.

    Four boards are registered and refused. LinkedIn, Indeed, Glassdoor and Naukri forbid automated collection and sit behind bot protection; getting past either is the one thing this system will not do. They stay first-class entries so the screen can name the board, give the reason, and point at what carries its postings — a board missing from your list is never a mystery. Naukri is the one that costs real coverage in India, and it says so.

    Provider states

    Enforced, not documented

    A 401, 403, 429 or CAPTCHA page raises and blocks that host for the run. There is no retry with different headers, no rotation, nothing that solves anything — the refusal is the whole response.

    Free-web page fetches check robots.txt first. An API called with your own key does not: that is a sanctioned client, not a crawler.

    05 · signing in

    Your email is the account. There is no password.

    Two ways in: Google's consent screen, or a six-digit code emailed to the address. The user table has no password column, there is no hashing anywhere, and no route accepts one — a test asserts the absence rather than trusting it. The rule was never to request or store mail credentials, and the cheapest way to keep a promise like that is to have nowhere to put one.

    Google is the authorization-code flow with PKCE, and identity comes from Google's userinfo endpoint called with a token this server fetched itself — so there is no ID token to verify and no crypto dependency. email_verified is checked: an unverified address is not an identity. One consent can cover Gmail too, read and draft only, so connecting your mail signs you in at the same time.

    Emailed codes are stored as a hash salted with the address, capped at five attempts, single-use, and expire in ten minutes. Sessions are signed with a secret generated once at 0600 outside the database, so a database backup cannot mint one.

    Sign-in surface

    Sign-in turns itself on as soon as a method is configured. With neither, the API stays open — the single-user localhost case — rather than locking a door with no key.

    06 · your résumé is the query

    Upload it once. The searches come from it.

    A .docx is a zip with XML inside, so it is read without a dependency; .txt and .md read directly, .pdf needs one optional package. Parsing is structural and deterministic — no model — so employers, titles, date ranges and bullets come out of a résumé in any field. A veterinary practice manager's CV parses with the same machinery as a network engineer's.

    The search terms are your own job titles, most recent first. Nothing was typed into a settings box, and nothing about your field is hard-coded.

    Everything the parser reads lands unverified — this is the one place in the system that infers career facts rather than being told them, so its output is second-class by construction. You confirm the accurate items, and only then can a résumé cite them. A recruiter asking about a bullet you never wrote is the failure this prevents.

    Read from one résumé

    What it could not find, it says

    No employment entries, no bullets, no dated roles — each produces a named warning rather than a confident-looking blank. An undated role is flagged, and the years-of-experience figure says it is understated.

    07 · applying, every four hours

    It applies where the employer published a route.

    Find, prep, apply, track — on a timer, within rules you set. Where a posting can legitimately be submitted to, it is. Where it cannot, the packet is finished and waiting, which is a click rather than an hour.

    Going live is two separate switches. Turning off the dry run makes each ready application wait for your yes; only turning off “ask before each send” as well makes it fully hands-off. Approving re-runs every guardrail at that moment, so a deadline that passed overnight still stops it.

    On the four boards that are not automated

    LinkedIn, Indeed, Naukri and Glassdoor all need an authenticated session as you, plus getting past bot protection, to submit. Doing that would mean holding your logins for those sites and defeating a control each put there deliberately — and it reliably gets accounts restricted, which costs more than the time it saves.

    So their postings still reach you through Google Jobs and the aggregators, and applying to them is assisted: tailored résumé, cover letter and pre-filled screening answers ready, you press submit. An application address in the description does beat a login wall — the employer published it, so using it is not a workaround.

    A tier is a ceiling, not a promise. A board in the API tier that answers with a CAPTCHA hands that one back to you. Nothing here solves a challenge, replays a token or retries with different headers.

      08 · getting past the screen

      Their words for your experience. Not their words for someone else's.

      ATS screening is substring matching. Two résumés describing identical work score differently because one wrote microsegmentation and the posting wrote micro-segmentation. Closing that gap is legitimate, and it is the only thing this does.

      The keywords come from that posting's own text — there is no industry list anywhere in the repository, which is why a veterinary role and a quantitative trading role are both scored properly. Every term then gets one of five verdicts, and only one of them results in anything being written.

      The rule is narrow and absolute: a term is added only when your evidence already supports the capability it names. The claim never changes, only the wording. A term nothing supports is reported as a gap and left off — the honest answer to a missing keyword is to get that experience, not to type the word.

      Only the skills index gains vocabulary. Bullets are left alone: a bullet is a specific claim about something you did, and rewording it risks changing what it says.

      The alignment runs before the factuality gate — on purpose

      Anything it adds is re-derived from the finished text and checked against evidence like any other claim, so a mistake fails the résumé rather than shipping. That paid for itself twice while this was being built: the gate caught the aligner trusting a skill id the checker cannot re-derive from words, and then caught a subtler one — a phrase's printed words can claim more than the phrase resolves to. “ospf troubleshooting” yields both network_monitoring and routing_switching, and only the first was being verified.

      Both now apply exactly the gate's standard: every skill the printed words yield must be supported. Which then surfaced the same class of bug one layer up, in a summary line that had been emphasising skills no bullet mentions.

      09 · evidence

      A résumé is a query over verified facts.

      Your history is stored as atomic facts — a project, a technology, a responsibility, an achievement, an employer, a date range — each one marked verified by you or not. A tailored résumé is assembled by selecting from that set, never by writing prose about you.

      Before any résumé can be marked final, a checker re-derives every entity in the finished text and matches it back to the evidence that supports it. The checker never calls a model; it is arithmetic over sets, so it cannot be talked around. A claim with no supporting evidence fails the document.

      The consequence shows up as omissions. If a posting wants SAP Firefighter and nothing in your evidence supports it, the requirement is simply left unclaimed — visible to you, absent from the résumé.

      10 · authorization

      Silence is never read as a yes.

      Work authorization is decided by a country pack — a plain data file of statuses and the phrases that signal them — applied to the posting's own words. It is not a model output, and the agent has no tool that can set it.

      If a posting says nothing about sponsorship, the verdict is unknown, not "probably fine". Every verdict quotes the phrase it was drawn from, and every verdict carries the same disclaimer, because none of this is legal advice.

      Adding a country means adding a YAML file. The United States pack carries 13 authorization statuses; India's carries its own employment and salary conventions, down to reading ₹ LPA as an annual figure.

      Unknown Sponsorship not mentioned
      We are unable to provide visa sponsorship for this position. Drawn from the posting · verdict: not compatible · AI assessment — verify with employer/recruiter.

      11 · coverage

      No job category is written into the code.

      The 15 seeded domains are a prior, not a schema. A posting that matches none of them well enough — below a confidence floor of 0.18 — is classified into a domain the model names itself, and stored under that new identifier. Nothing in the pipeline needs to know the list in advance.

      ATS keywords are derived per posting from that posting's own text. There is no industry word list anywhere in the repository, which is exactly why a veterinary role and a quantitative trading role both work without anyone adding them.

      Seeded domains — extended at runtime

      Highlighted domains appear in the demo set. Plus anything else a posting turns out to be — one role here lands in other on purpose.

      13 · running it

      The demo is frozen. The system is not.

      Everything above is captured output. To run the real thing — live job sources, a real agent loop, Gmail drafts that wait for your approval — clone the repository and start the API. It works with no model key at all; the key only turns on the agent and the LLM classifier.

      # backend, tests, and the API pip install -e . careeros init --sample careeros serve # the web / iOS / Android client cd clients/app && npm install && npx expo start
